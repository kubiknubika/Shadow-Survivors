# Проверка Android-сборки без телефона

Просьба: «Проверь что всё работает, насколько можешь». Здесь — что именно
прогнано, чем и с каким результатом. Всё, что нельзя проверить в этой среде,
названо прямо; ничего не объявлено работающим без прогона.

Среда: Linux, **нет** Windows, JDK, Android SDK, NDK, mingw и телефона.
Поэтому проверяется то, что видно из файлов и стендов, а APK не собирается.

---

## Одной командой

```
python3 tools/check_android_bat.py --strict     # батник, проект, инструкция
bash tools/check_android.sh                     # андроид-слой + ядро + чекер выше
python3 tools/check_version.py --strict         # версия везде одна
python3 tools/build_update_bat.py --check       # update.bat = исходник
```

Плюс исполняющие стенды (их же запускает `tools/check_android.sh`):

```
bash tools/check_android.sh          # синтаксис + чекер + оба стенда
bash tools/check_android.sh --quick  # без исполнения (быстро)
```

И отдельно, если нужны только замеры и картинки:

```
g++ -O2 -std=c++17 -pthread -Isrc tools/screen_check.cpp -o build/screens
build/screens 1 1 > a.txt && build/screens 4 1 > b.txt && diff a.txt b.txt
g++ -O2 -std=c++17 -pthread -Isrc tools/perf_bench.cpp -o build/perf && build/perf 300 1280x720 2
g++ -O2 -std=c++17 -pthread -Isrc tools/touch_preview.cpp -o build/touch && build/touch 1600x720 build/touch.bmp 1
```

Абсолютные числа тут ничего не доказывают: эта же машина в соседних прогонах
даёт 5,4 и 7,2 мс на одном и том же кадре (энергосбережение и соседи по хосту).
Поэтому регрессию проверяют сравнением, а не цифрой: сцена 2.10.55, собранная из
`HEAD`, и 2.10.56 дают **одинаковый хеш кадра** `fd4cb23a` и одинаковое время
в пределах дрожания.

Сцена `trail` тяжелее базовой на 0,5–0,7 мс в альбоме — и это не цена предмета:
в портрете та же сцена с тропой, наоборот, быстрее базовой (4,25 против 4,85 мс).
Разница — сама сцена: в `trail` герой бежит, за ним идут 56 врагов, а в базовой
он стоит и вокруг 19 врагов. Цена предмета измерена отдельно и лежит выше.

## Что нашлось и исправлено

### `build_android.bat`

1. **Версия Java не читалась при JDK из Android Studio.** Команда стояла внутри
   `for /f` в кавычках, а путь `C:\Program Files\Android\Android Studio\jbr`
   содержит пробелы: cmd резал его на `C:\Program`. В журнал попадало
   `Java: unknown`, а предупреждение «JDK старше 17» срабатывало ложно.
   Теперь `java -version` пишется в `build\java_version.txt`, а версия читается
   из файла — пробелы в пути больше ни на что не влияют.
2. **Кириллица в хвосте журнала.** `Get-Content` без `-Encoding` в Windows
   PowerShell 5.1 читает файл как ANSI, и русский текст из журнала превращался
   в мусор именно в тот момент, когда его читают. Добавлено `-Encoding UTF8`.
3. **Путь к `adb`** собирался со слэшами вперёд — теперь зовётся обычным путём
   Windows.
4. **Код возврата** был всегда 0. Теперь 1 при ошибке; двойной щелчок
   по-прежнему упирается в `pause`, а из скрипта результат видно.
5. **Предупреждения** про отсутствующие NDK и platform-tools: раньше это
   всплывало позже и непонятнее.

### Новый стенд `tools/check_android_bat.py`

Проверяет то, что руками проверять больно и что ломается тихо:

- **батник** — UTF-8 без BOM, только CRLF, метки и переходы, баланс скобок в
  блоках `if`, кавычки в `set`, объявленность каждой `!переменной!`,
  отсутствие команды в кавычках внутри `for /f`;
- **проект** — `lib_name` в манифесте против имени CMake-цели, глубину `../`
  до `src/`, `applicationId`, `ndkVersion`, `minSdk`, `targetSdk`, `abiFilters`,
  `hasCode="false"`;
- **инструкцию** — версию и `versionCode` по умолчанию в
  `android/app/build.gradle` против `src/version.h`, существование каждого файла
  и каталога, названного в `ANDROID_BUILD.md` и `design/android.md`.

### Чем проверен сам чекер

Он не должен быть «всегда зелёным», поэтому проверен мутациями: в батник и
проект по одному вносились настоящие поломки, и каждая должна была быть
поймана. Восстановление файлов проверялось после каждого шага.

| поломка | поймана |
|---|---|
| переход на несуществующую метку | да |
| незакрытый блок `if` | да |
| LF вместо CRLF | да |
| необъявленная `!переменная!` | да |
| команда в кавычках внутри `for /f` | да |
| `lib_name` не тот, что CMake-цель | да |
| версия в gradle отстала | да |
| `versionCode` в gradle отстал | да |
| CMake ищет `src` не на той глубине | да |
| инструкция ссылается на удалённый файл | да |
| инструкция потеряла разбор ошибок | да |
| манифест без `hasCode="false"` | да |

12 из 12. Двенадцатая поломка случилась по-настоящему: после правки в батнике
остался одиночный LF, и чекер упал на нём сразу, до коммита.

## Главное: Android-слой теперь исполняется

Синтаксическая проверка отвечает «компилируется», но не «работает». Поэтому
появился стенд `tools/android_smoke.cpp` и поддельный NDK
`tools/android_host/` — около 60 функций EGL, GLES2, AAudio, ALooper,
AInputQueue, ANativeWindow и ассетов, реализованных по-настоящему:

- события ввода идут через ту же `AInputQueue_getEvent`, что и на телефоне;
- кадр уходит в `glTexSubImage2D`, а стенд хеширует то, что «показано»;
- AAudio сам зовёт аудио-колбэк по 512 кадров, как это делает система;
- ассеты читаются с диска, как из APK.

Стенд поднимает активность, отдаёт ей окно 2400×1080, шлёт касания и клавиши,
уводит приложение в паузу и возвращает, меняет размер окна и закрывает его.
38 проверок (в 2.10.53 добавились 11 про управление), все проходят:

| что проверяется | как |
|---|---|
| кадры доходят до экрана | счётчик `eglSwapBuffers` растёт |
| логический кадр телефона 20:9 | `1600×720` при окне 2400×1080 |
| поля вместо растяжения | окно 1920×1000 → кадр 1376×720, пропорции сохранены, есть поля |
| касание двигает героя | `playerX` растёт после касания слева-снизу |
| первый запуск спрашивает схему | сразу после старта состояние `STATE_CONTROLS_SETUP` |
| карточка выбирает схему | касание второй карточки даёт `TOUCH_SCHEME_STICK_RIGHT` |
| «ДАЛЬШЕ» сохраняет | `touchSetupDone = 1`, состояние ушло с экрана |
| выбор лежит в файле | 68 байт, по `offsetof` схема `1` и флаг `1` |

### Что этот стенд уже нашёл

**`touchUpdate` стирал клавиатуру.** Каждый кадр, если пальца на стике нет,
функция обнуляла `keyW/A/S/D`. На телефоне это значит, что физическая
клавиатура (планшет, Chromebook, Android TV с геймпадом) работала ровно один
кадр: `AKEYCODE_D` ставил флаг, а следующий `touchUpdate` его снимал. Сброс
убран — отпускание пальца снимает флаги само (`touchEnd`), а зависший палец
закрывается `ACTION_CANCEL`. Нашла это проверка «`AKEYCODE_D` ставит `keyD`».

## Чего проверить нельзя и как это проверить вам

| не проверено | почему | чем проверяется |
|---|---|---|
| сборка APK | нет NDK, JDK и Windows | `build_android.bat` → `build\android_build.log` |
| запуск на телефоне | нет устройства | `build_android.bat install`, затем `adb logcat -s ShadowSurvivors`; логика слоя уже прогнана стендом `android_smoke` |
| звук на телефоне | AAudio требует устройства | первый запуск: тема должна играть, пауза — замолкать |
| сборка `.exe` | нет mingw, а `main_win32.cpp` без `windows.h` не собрать | `build_windows.bat` у вас |
| размер кнопок под большой палец | нужен живой экран | пройти три схемы и ступени размера в бою: 100 % — кнопки `СУПЕР`/`РЫВОК` 92 px, крестовина 62 px с шагом 68, база стика 58 px; 80 % — 74/50/46, 160 % — 147/99/93; мёртвая зона 14 px |
